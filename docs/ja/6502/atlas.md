# チップアトラス: すべての部品に住所を

`web/{groups,graph,schematic,timing}.json` から `tools/export-atlas-doc.py` が
生成している。以下のどれも手で打ったものではない。ダイデータか導出を変えたら
作り直せば、この文書が付いてくる。

このダイの上のノード、トランジスタ、ワイヤはそれぞれちょうど一つのアドレスを
持ち、アドレスの接頭辞はその下にある集合を名指す正当なやり方になる。狙いは
ホスト名ではなく IP アドレスだ: 前が経路を決め、後ろが同定する。

**8365 アドレス**: ノード 1547、トランジスタ 3510、ワイヤ 3308。すべて一意で、
すべて解析できる。このファイルが書かれる前に生成器が検査している。

## 書き方の規則

```
<container> : <class> : <slot>
```

**右から解析する。** スロットは最後のコロンの後、クラスはその一つ前、そして
コンテナは残り全部だ。フィールド数を固定するやり方は使えない: コンテナのキー
は正当にコロンを含むことがあり (`alat:ADL/ABL`)、束は二つのコンテナを名指す
(`regs:a~sbus:sb`)。

### 区切りがコロンである理由

これを決めたのは趣味ではなく、ダイだ。707 個の名前にわたって使われている
約物は `# ( ) + - . / _` で、コンテナのキーが `:` を足す。ダイの名前にコロンは
**一つも**現れないし、`kind:id` はこのプロジェクトが他のどこでもコンテナを
綴るやり方でもある。`.` と `/` はどちらも落ちた: `.` は 33 個の名前と 14 個の
キーに、`/` は 47 個と 5 個にある。

### 三つのフィールド

| フィールド | 何か | 出どころ |
|---|---|---|
| **container** | その部品が属する導出されたグループ | チップマップの分割: 23 種類にまたがる 132 グループ、どのノードもちょうど一度 |
| **class** | プルダウン網の形。NMOS ではそれが**そのまま**ブール関数だ | `schematic.json` が認識したゲート |
| **slot** | その部品に対するダイ自身の番号 | 読み取り専用のサブモジュール経由の `segdefs.js` / `transdefs.js` |

### スロットはダイの番号であり、そこが荷重を受けている決定

他のフィールドはどれも導出であり、ここでの導出は動く: チップマップは、争わ
れているノードをどの種類が持つかを既に変えているし、割り込みの歩き方は
その所有の規則を既に変えている。最後のフィールドが導出であるようなアドレスは、
そうした改善のたびに壊れることになる。

生成器はその性質を主張する代わりに証明する。種類の所有順を逆にすると
**1547 ノードのうち 88 の持ち主が変わり、スロットは 0 個動く**。

だから接頭辞は改められる主張であり、スロットはそうではない。アドレスを最後の
フィールドまで削っても、その部品はまだ見つかる。

### クラスの語彙は閉じていて、34 語ある

NMOS に AND ゲートは無く、OR ゲートも無い。プルアップが出力を high に保ち、
接地へのプルダウン網がそれに勝つので、どの静的ゲートも積和の反転だ: 並列な脚
が OR、直列なトランジスタが AND になる。だから脚の内訳は、ゲートに付けた札
ではなく、そのゲートが計算するものの完全な記述だ。`aoi2.1` は
`NOT((A AND B) OR C)` である。

### 事実はタグとして乗り、フィールドにはならない

アドレスに要る識別子はちょうど一つで、それは不変でなければならない。部品に
ついて他に真であることは、すべてタグだ: 問い合わせられて、順序を持たず、何も
動かさずに変わっていい。

```
sbus:sb:bus:#1188                  name=sb3  bit=3@sb  depth=6
regs:x.SBX:dyn3:#1186              name=dpc3_SBX  opens=8  precharged  phase=phi1  depth=5  also=sbus:off  also=dpc:phi1
regs:a:bus:#737                    name=a0  bit=0@a  depth=7
clock:gen:dyn5:#943                name=cclk  opens=243  precharged  depth=4
```

`bit=` はトレーサが実測したバスの幹の規則 (文字だけ、`not` の補数は無し、
ビット 0 に名前があり、ビット 0..7 のうち少なくとも七つ) を使い、**24 本の幹**
に落ち着く。`depth=` は最も近いピンからのホップ数。`phase=` はチップを走らせて
実測している。`also=` は、重なり合う層ではこのノードを自分のものだと言うが、
分割では取り負けたコンテナを名指す。

## 名前はどこから来たか

どれも私たちのものではないので、述べておく価値がある。答えは三段深い。出どころ
は保存アーカイブの `6502_datapath.wiki` だ。

| 体系 | 例 | 何か |
|---|---|---|
| **Hanson** | `Y/SB`, `SB/X` | `SOURCE/DEST`。MOS の設計図から描かれたブロック図のもの |
| **Balazs** | `R1x7`, `Dkx2` | 位置の格子。彼自身のダイ写真から |
| **JSSim**、そして私たちのもの | `dpc4_SSB` | 位置の接頭辞に、Hanson の名前を**足したもの** |

だから制御線の名前は、半分が座標で半分が機能だ。接頭辞は本物の順序になって
いる: 線を `dpc` の番号で並べるとダイを左から右へ並ぶ順になり、43 本のうち
6 箇所の逆転はすべて隣どうしの組だ。番号が負のものが二つ、`dpc-1_ADL/ABL` と
`dpc-2_ADH/ABH` があるのは、アドレスラッチのロードがデータパスの番号が始まる
場所より左に座っているからだ。

`tools/check-dpc-vs-wiki.py` は wiki の主張をチップに問い直す。

これらは分割ではノードを一つも自分のものにしていない。中にあるものはすべて、

| コンテナ | n | なぜ吸収されるか |
|---|---|---|
| `sbus:link` | 1 | 特殊バスが丸ごと吸収する |

## アドレスが教えてくれないこと

- **向き。** パス・トランジスタは両方向に導通するので、トポロジだけではどちら
  の端がソースなのかを言えない。Hanson の `SOURCE/DEST` の名前だけがその記録
  であり、あれは書き下ろしで、実測ではない。
- **近所。** `depth=` はピンからのホップ数で、距離であって近所ではない。
  「2 ホップ以内に何があるか」は問い合わせであって、座標ではない。
- **どのコンテナが*いちばん*面白いか。** 分割は箱を描けるように持ち主を一つ
  選ぶ。残りは `also=` が運ぶ。
- **ノード 866 について何でも。** これは `inert` に分類され、それは正しい:
  トランジスタ一つをゲートしているが、チップの中のどれもそれを駆動できない
  ので、どんな走行も決してそれを観測できない。
